## `epsfcn`, measured — the small concrete thing, settled

`next_steps.md`'s x109 paragraph carried a parenthetical "correction" reading
*"`_audit/closed/x109_hypotheses.md` says `epsfcn = 0.01`; the value is `1.0e-3`, matching
`_harness/finite_difference.py`'s `PROCESS_EPSFCN`"*. **That correction was itself wrong.**
`1.0e-3` is the *default* (`process/data_structure/numerics.py:595`), which is correctly
what `PROCESS_EPSFCN` carries; it is not the value on the file the investigation ran on.

Measured on all seven reference configurations. `epsfcn` is set by `init_process` from the
input file, so it needs no solve: `SingleRun(path, "vmcon").data.numerics.epsfcn` is the
same field `reference_run(path).epsfcn` reports, and reading it that way cost seconds
instead of seven ~100 s runs.

| configuration | `epsfcn` | source |
|---|---|---|
| `stellarator_helias` | **0.01** | `IN.DAT:230`, an explicit override |
| `helias_5b` | 0.001 | default |
| `large_tokamak_nof` | 0.001 | default |
| `large_tokamak_eval` | 0.001 | default |
| `low_aspect_ratio_DEMO` | 0.001 | default |
| `spherical_tokamak_eval` | 0.001 | default |
| `st_regression` | 0.001 | default |

`stellarator_helias` is the **only** file in the set that overrides it, and its own inline
comment says why: *"Default for this parameter is 1e-3 however this specific IN.DAT and
starting point benefit from a larger step length."* `st_regression.IN.DAT:46` looks like a
second override but is commented out (`*epsfcn = 0.001`), so it lands on the default in any
case.

**Three consequences.**

1. The x109 argument is *strengthened*, not weakened: the finite difference PROCESS uses on
   this file is `0.01`, ten times wider than the record's "correction" claimed and ~10^5
   times wider than the `1.9e-09` the port's answer sits from the kink. `x109_hypotheses.md`
   was right the first time.
2. **`_harness/finite_difference.py`'s `PROCESS_EPSFCN = 1.0e-3` is a defensible default and
   a misleading one for the reference stellarator.** Tier-1 gradient agreement on units
   drawn from `stellarator_helias` is being checked against a finite difference ten times
   *finer* than the one PROCESS itself takes on that file. This is not a bug — the error bar
   is Richardson-derived per point, not a fixed `rtol`, so a finer step is a legitimate and
   in fact stricter oracle — but the constant's docstring should say "the default", not
   imply "PROCESS's". Not changed here; `finite_difference.py` was outside this pass.
3. Anything that quotes "PROCESS's `epsfcn`" without naming a file is ambiguous across the
   reference set, and one such sentence has already been wrong once.

Corrected in place: `next_steps.md`'s x109 preamble paragraph, and §25's `epsfcn` bullet
(which had the right answer for `stellarator_helias` but had not measured the other six).

## The recovered diff: superseded, not applied

`a2c20704-drivers.diff` replaces `VmconDriver.__call__`'s inline unfloored
`np.divide(1.0, flat_start, out=scale, where=flat_start != 0.0)` with
`design_scale(flat_start)`, so the VMCON path picks up the `UNSCALABLE_BELOW = 1e-12` floor
that only the SLSQP path had. That is claim #8, and it is exactly the "Open" defect
`next_steps.md` §11.11 records.

**Verdict: superseded. Do not apply — and it was not applied.** The same fix has since
landed in the main tree, in a better form than the patch: `drivers.py:750` calls
`design_scale`, and rather than the patch's five-line inline comment the case that found
the bug (`.power.qac` exactly `0.0` seeded, `-3.8e-27` solved, scale `-2.6e+26` on restart,
reachable only by restarting) is written into `design_scale`'s own docstring, where it
serves both callers instead of one. The patch also fails mechanically: `git apply --check`
rejects it in both directions, because the surrounding comment block it patches no longer
exists.

Nothing in the diff is worth salvaging. The one thing it carries that the tree does not is
its rationale-in-a-comment, and the tree's version of that rationale is longer and better
placed.

## What is actually open on `x109` {#open}

Unchanged from `x109_hypotheses.md` §8, re-checked against this tree and re-ordered by what
this pass thinks is worth doing:

1. **Give SAND a Stage B0.** Claim #13. AD against a central difference of the SAND
   condition map at the answer — the check that found the `c24` kink in 2 of 690 cells, and
   the only thing in the repo that looks for this failure class at all. Note it is a
   *different* class from the audited one (`next_steps.md` §9, §10.5b, §11.8 are about `nan`
   derivatives **at exactly zero**; this is a finite derivative on one side and an unbounded
   one on the other). It should be a committed instrument, not a scratch script — see
   claim #15.
2. **A fix for the kink itself.** Not attempted, and the three options are different in
   kind: declare the `temp_sum_20 > 0.65` switch as an `Alternative` so the two arms are two
   smooth problems (claim #2 notes this has *not* happened despite a neighbouring switch
   being converted); give the SQP a trust-region safeguard; or leave it and record that the
   port's answer is the ridge. Choosing needs a view on whether PROCESS's model is *meant*
   to be differentiable there, which is a PROCESS question.
3. **How wide the ridge is.** `0.0305`, `0.0315`, `0.0325`, `0.0334`, `0.0336` would not
   converge from continuation, so whether `phi` is genuinely non-monotone between `0.0300`
   and `0.0310` is not settled by anything on record.
4. **The pinned-solve failure mode.** 1 of 14 fine pins around the free optimum converged to
   full feasibility, and the failures are catastrophic (`objf 3.29` with `max|eq| 1.79`; one
   pin returning `objf 1.02e+23`) rather than stalls. Continuation does not rescue this
   problem and success is not monotone in step size — a caveat for any future pinning study.
5. **`x56`.** Untouched. Read as a flat direction (claim #7) and nothing disturbs that.

## The lesson this pass adds

The project's recorded failure mode is *an argument stated before the measurement that
would settle it*. This pass found the neighbouring one, twice, and both cost real work:

- **A correction issued without the measurement.** The `epsfcn` parenthetical was a
  confident correction of a *right* number to a *wrong* one, made by reading a default out
  of `numerics.py` instead of reading the field off the run. It survived long enough to be
  half-corrected in §25 and left uncorrected in the paragraph §25 was correcting.
- **A measurement re-commissioned after it was taken.** §17.2 called for a measurement, and
  called it the highest-value one left in the ladder, five days after §11.11 and two closed
  records had answered the same question by a better method. The cost was not the
  measurement — it was that this task was scoped around re-opening it.

Both have the same shape: **the record was long enough that its own contents were cheaper
to re-derive than to find.** That is an argument for indexes like this file, and against
letting `next_steps.md` grow another 4000 lines without one.
