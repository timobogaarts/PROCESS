Uncut dependency graphs

Design structure matrices (DSMs) of the PROCESS port's dependency graph, as declared — before any cut, driver, or optimisation problem is added to it.

These are the graph as declared, not as run. The port models PROCESS as a graph of named nodes with typed inputs and outputs. The pages below show that graph uncut and undriven: no feedback loop has been broken, no algorithm has been chosen to solve it, no optimisation problem has been laid on top. That matters for reading the "SCC" pages in particular — a strongly connected component (SCC) there means these nodes are mutually coupled, not "this is the order they run in." A raw cycle has no order; only after a cut assigns it a driver does a run order exist at all.

Two orderings, on two reference machines, give four pages. Provenance ordering groups nodes by where they were written in the source — subsystems laid out in their dependency order, each given a colour band. A mark below the diagonal inside one colour band is a place where provenance and dependency disagree within a subsystem; a mark below the diagonal across bands is real feedback between subsystems. SCC ordering instead groups nodes by strongly connected component, so any coupling — within or across subsystems — is visible as an off-diagonal block rather than scattered marks.

The headline measurement (see functional_process/_audit/uncut_graph.md for the full account): on the reference stellarator, the uncut graph has 144 blocks, of which 2 are genuinely coupled; on the reference tokamak, 223 blocks, of which 3. Cutting those loops to make them solvable changes zero block counts on either machine — every cut lands inside an SCC that already existed uncut, it just gives that SCC an algorithm. PROCESS's declared dependency structure is almost entirely acyclic, and the coupling that does exist is small, local to one subsystem, and does not cross subsystem boundaries on either machine measured.

Reference stellarator (stellarator_helias.IN.DAT)

  • Provenance order
    Nodes grouped by subsystem, subsystems in dependency order. Best view for seeing how one subsystem's internals relate to the next.
  • SCC order (mutual coupling, not a run order)
    Nodes grouped by strongly connected component. Two blocks are genuinely coupled here: a 6-node cycle inside physics (fusion power and density profile) and a 2-node cycle inside stellarator (divertor / first-wall area). Everything else is a singleton.
